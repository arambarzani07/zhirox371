# V43 — Purchase-order pagination and exact actions

Purchase-order history now reads canonical, store-scoped PostgREST pages of 50 with exact counts and stable created-at/ID ordering. Server search selects order number, recorded supplier name, recorded product name or note and escapes literal wildcard characters. Supplier-ID and all four schema statuses (pending, ordered, received, cancelled) are server filters. Recorded names are used in rows/printing so renamed cached profiles do not silently change an order's historical description.

The four KPIs and CSV describe the displayed server page. CSV includes full order IDs and its page range/count in the filename. Pending cost uses checked monetary sums. Loading, denial, a new query and logout clear old rows, monetary KPIs and printable details. Empty final pages recover after counts shrink. Read and action tokens reject obsolete replies.

Every print/receive/cancel action first fetches the exact current order by store and ID. Changed status blocks receiving/cancellation; PurchasingV23 retains its atomic pending-status condition on the actual cancellation update. Receiving hydrates the exact active supplier when it is outside the bounded mutation cache, preserves other selections and fills the exact order number, quantity and cost. If the order's product is absent from the receiving selector, the action stops instead of retaining another product. Print details use the newly fetched order rather than the first-500 cache.

Validation: 272 local Node tests and syntax/assets build passed. New tests cover 623 pages, literal and recorded-name search, status/supplier filters, safe quantities and sums, exact action IDs, changed-status rejection, missing-product rejection, stale actions/reads and shrinking pages. Manual PC QA traversed page 501–523 of 523; its CSV contained 23 rows/10 columns with full IDs. Fresh print and receiving details for PO-521 matched its supplier/product/quantity; cancellation of PO-521 in disposable preview data returned a cancelled row and removed receive/cancel actions. Browser and actual Auth/PostgREST CI scenarios are authored and syntax-checked, awaiting remote CI.

Limits: offset pages are live reads, not a repeatable snapshot. Supplier filter choices, order creation helpers and low-stock pending-order checks still use the bounded snapshot plus explicit supplier pins. Receiving cannot hydrate an out-of-cache product yet and fails safely in that case. Supplier account/receiving history is still bounded. Order/invoice numbering remains the existing client mechanism and needs a server-owned follow-up. No SQL/RPC definitions, grants, RLS, locked Home, production database or PC Relay changes.
