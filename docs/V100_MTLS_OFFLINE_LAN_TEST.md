# V100 — TLS 1.3 Mutual Device Authentication, Revocation and Offline Checkout Lab

**Release status: NO-GO** for actual LAN or supermarket cashier installation.

V100 builds on the signed two-device localhost gateway from V99. It is an
**actual TLS 1.3 mutual-certificate** and genuine disposable PostgreSQL
integration in GitHub CI. It still listens **only on 127.0.0.1**. We do
NOT claim that two physical Windows cashiers or a real network outage
were exercised.

## Verified trust boundary

- HTTPS uses a temporary, private **test CA** and ephemeral server/client
  certificates generated by OpenSSL in the CI runner; no keys or
  certificates are committed to Git. The server requires a client
  certificate, verifies the CA chain and accepts TLS 1.3 only.
- A client pins that test CA, requires a valid server certificate for
  127.0.0.1, and presents its own X.509 client certificate/key. It
  never sets `rejectUnauthorized:false`, falls back to HTTP or
  connects to a WAN address.
- After the TLS handshake, the API matches the authenticated client
  certificate's CN and SHA-256 fingerprint to the claimed device ID
  and the `zhirox_local.v100_trial_devices` registry in the **isolated
  PostgreSQL test database**. The DB record must be enabled.
- The V95 gate role can read only the minimal device registration
  columns; it has no INSERT/UPDATE/DELETE or financial table DML.
  Enrollment/revocation is carried out only by the disposable database
  owner in CI. The server queries the durable DB registry **on every
  HTTP request**, so revocation and cert replacement take effect
  without process restart.
- Device HMAC+nonce authentication from V99 and signed local user
  sessions, V97 HMAC proof with live session version, and atomic
  V90 FEFO sale remain required in addition to mutual TLS.
- The operator entrypoint requires
  `ZHIROX_V100_MTLS=YES_ISOLATED_V100_MTLS_TEST`,
  separate limited-role PostgreSQL URLs pointing to the disposable
  DB, and explicit test-only TLS paths/secret configuration.
  No real market keys, cloud credentials or Windows deployment are
  configured.

## Real CI acceptance

The synthetic fixture begins with **14 test receipts and 14 outbox
events** from V99. The test creates a fresh CA and certs for the server,
`trial-pc-01`, `trial-pc-02` and a replacement certificate. No
certificate/key data appears in logs or in backup.

- Connections **without a client certificate** fail.
- Two independently authenticated trial devices make simultaneous
  HTTPS checkouts against one shared PostgreSQL stock/FEFO LOT ledger.
- Revoking PC2 in the DB rejects its still-valid mTLS/HMAC/session
  credentials **before** it can create another sale. PC1 continues
  working without the internet.
- PC1 commits a sale, then loses its HTTPS response; it retries the
  identical immutable request ID/cart, recovering the original receipt
  with no duplicate outbox or stock deduction.
- Rotating the DB certificate fingerprint denies PC1's old cert
  instantly and permits a new CA-signed client cert for the same
  named test device.
- Final accounting **17 synthetic receipts, 17 synthetic outbox
  events, and exactly three base units** deducted from the water
  product and matching FEFO LOT balance; no physical transaction.
- Temporary SQL roles are reset to NOLOGIN and a PostgreSQL custom
  backup is retained as a CI artifact for up to 30 days. Ephemeral
  key/cert material is deleted in the disposable CI container.

## Remaining gaps

This is a cryptographically verified loopback lab, **not** actual
Windows 10 over two NICs / Wi-Fi AP and not a production-safe LAN
listener. The physical LAN test remains to be performed with device
certificate enrollment, secure OS-level private key storage, firewall
rules, TLS renewal and recovery, installer/service identity,
printer/scanner/UPS acceptance, durable multi-device replay tracking,
automatic backup restoration, and the local multi-cashier outage plan.

The gateway needs the local PostgreSQL and LAN server to remain
reachable; loss of the central on-site server is a different problem
from internet unavailability. An online/cloud replica must never
block cashiers. No production database, Supabase, PC Relay, DVR,
deployed supermarket machine, locked Sorani 12×4 Home or real inventory
is changed or deleted.
